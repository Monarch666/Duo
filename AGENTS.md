# AI Coding Agent Guidelines for Duo

Welcome, Agent. You are pair-programming on **Duo**, an intimate, private shared sanctuary built exclusively for exactly two partners. Every feature, database query, and UI component must uphold absolute couple privacy, rock-solid isolation, and refined tactile craftsmanship.

Before writing or modifying any code in this repository, study and strictly obey the rules below.

---

## 1. Non-Negotiable Core Laws

### 🔒 Law 1: Strict Data Access Layer (DAL) Scoping
- **NEVER** write ad-hoc database queries inside page routes, client components, or random helper files that bypass the DAL.
- All database read and write operations for couple resources (Events, Lists, Check-ins, Memories, Preferences, Notes, Moods) **MUST** go through `createCoupleDal({ userId, coupleId })` located at `src/lib/dal/index.ts`.
- Every query generated by the DAL must be cryptographically bounded to the authenticated session's `coupleId`. Any cross-couple data leakage is considered a critical security failure.

### 👥 Law 2: Hard 2-Member Couple Limit
- A couple space consists of **at most two members** (`creator` and `partner`).
- Never introduce any mechanism, role, or bypass that allows a 3rd member to view or join a couple space.
- The `joinCoupleSpace` action must always verify `count(coupleMembers) < 2` before creating an association.

### ✉️ Law 3: Reciprocal Check-in Vault Secrecy
- In the Weekly Rituals module (`src/lib/dal/checkins.ts`), check-in reflections are strictly confidential until **both** partners have submitted their answers for that week.
- If only one partner has submitted, the API/DAL must **never** send the other partner's response to the client. Responses may only be unsealed side-by-side once both answers exist.

### 🎨 Law 4: Strict Aesthetic Guardrails (Anti-AI Slop)
- Duo is designed with an editorial, tactile, papercraft aesthetic.
- **FORBIDDEN**:
  - No generic neon cyan/purple/pink gradients.
  - No tacky frosted glassmorphism (`backdrop-blur-md` on full backgrounds).
  - No random decorative emojis sprinkled in corporate UI style.
- **REQUIRED**:
  - Warm parchment canvas (`#FAF6EF` / `warmth-100`).
  - Solid card surfaces with warm borders (`border-warmth-200/80` or `border-warmth-300`).
  - Editorial serif headings (`Fraunces` / `Playfair Display`) paired with clean sans body (`Plus Jakarta Sans`).
  - Tactile physical metaphors: polaroid photo frames, washi-tape tabs, wax-sealed envelopes.
  - Always consult `DESIGN_SYSTEM.md` before adding or styling components.

## 2. Technical Stack & Conventions

### 2.1 Next.js 16 & React 19 Patterns
- **Server Components by Default**: Pages like `src/app/page.tsx` fetch data on the server via authenticated sessions and pass initial state down to client components.
- **Server Actions for Mutations**: All state modifications (creating events, ticking list items, updating moods) must use Server Actions (`'use server'`) inside `src/lib/actions/`.
- **Validation**: Every Server Action must validate inputs using **Zod** schemas defined in `src/lib/validations/index.ts`. Never trust raw user inputs.
- **Optimistic UI**: Client components should update local state optimistically where appropriate, reverting if the server action returns an error.

### 2.2 Database & Migrations
- **ORM**: Drizzle ORM (`drizzle-orm`).
- **Current Dialect**: SQLite via `better-sqlite3` located at `./data/duo.db`. WAL mode enabled.
- **Supabase Migration Path**: When switching to Supabase PostgreSQL, map types from `drizzle-orm/sqlite-core` to `drizzle-orm/pg-core` without altering column semantic meaning.
- Run `npm run db:push` to apply schema updates; run `npm run db:seed` to seed local demo data.

### 2.3 Realtime Event Bus
- Realtime events are published through `publishCoupleEvent(coupleId, event)` in `src/lib/realtime/bus.ts`.
- Broadcast events to the client using Server-Sent Events (SSE) via `/api/realtime/sse` with a fallback 5-second polling route at `/api/realtime/poll`.
- When deploying to Supabase, route this bus through Supabase Realtime Channels.
